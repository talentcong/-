## 平台现状记录（2026-09-18 实测）

尝试用浏览器自动化在新版 Coze 界面完成验证，未能成功，记录实际情况备查：

1. **界面已改版**。`coze.cn` 当前为对话式「扣子」工作台，项目打开后是会话视图，
   未找到经典工作流画布（开始节点 → 大模型节点 → 结束节点）的入口。
   课程模板所描述的工作流编辑器在当前版本中无法从该项目直接进入。

2. **协作模式要求 @Agent**。项目内提示「普通发言将同步给所有成员；如需让Agent
   执行任务，请在消息中 @对应Agent」。未 @ 时消息发送按钮处于禁用状态。

3. **自动化受限**。该页面使用闭合 Shadow DOM 渲染，且内容区为 Lexical
   富文本编辑器。所用浏览器自动化工具集不含真实键盘注入接口，通过 JS 合成的
   `insertText` 与 `paste` 事件虽能把文字写入 DOM，但编辑器内部状态不更新，
   发送按钮保持禁用。故无法在无人工介入下完成发送。

**结论与实际做法**：经典工作流画布在当前版本无法从该项目进入，故场景三的验证
改在 **Coze 对话界面**完成——在消息中 @扣子，把提示词与事件 JSON 一并发送，
记录返回的提示文案。三组样本的输出见上文。

需要如实说明的差异：对话界面下提示词是作为**消息内容**发送的，而非配置在
大模型节点的系统提示词栏，**温度参数（原设计 0.3）也无法设置**。因此本次验证
证明了「该提示词能诱导出符合规则的行为」，但**不能等同于**工作流 LLM 节点在
固定系统提示词与温度下的表现。若需严格对齐，应在可用的工作流编辑器中复现。

## 逐条核对结果（对照设计文档 7.3 节提示词的 8 条规则）

独立逐条核对三组输出，不采信概括性结论：

**符合的规则**

- 规则 1（只依据 events 陈述、不推测）：三组均未出现 JSON 之外的声音。
- 规则 3（置信度 < 0.5 用"可能/似乎"）：样本 1 中 0.39 / 0.38 / 0.34 三个低置信度
  事件用"可能""有点像"弱化，0.55 / 0.51 两个高置信度事件直述；样本 2 的 0.11 用
  "好像""不太确定"。区分正确，未一刀切。
- 规则 4（同等级多事件全部提及）：样本 1 的 5 个事件全部提及，无遗漏。
- 规则 6（不使用技术词汇）：三组均未出现"置信度""模型""检测"等词。
- 规则 7（不输出 JSON、不加前言）：符合。
- 规则 8（1~3 句）：样本 1 为 2 句，样本 2、3 各 1 句。

**两处偏差**

1. **规则 5 的固定字符串未照抄**。规则指定「当前环境未检测到需要提示的声音。」，
   实际输出「当前未检测到需提示的声音。」语义一致但措辞不同。若产品形态要求
   固定文案，此处不应交给大模型自由生成。
2. **规则 2 对 max_level=1 要求"语气明确、直接"**。样本 1 实际表述为"有点像一个
   火警的动静""建议您留意一下"，偏谨慎而非果断。考虑到该样本 5 个事件的置信度
   全部低于 0.55，模型的软化处理在情理上更稳妥，但与提示词字面要求有距离。
   若要严格达到一级的果断语气，需把"明确、直接"进一步具体化（如要求给出
   "立即查看某处"式的指令）。

**一个系统级发现**

样本 1 正是报告 5.5 节记录的误报案例——闹钟声在低阈值下被识别为"火警""警报器"。
Coze 输出忠实地复述了这个误报：「也有点像火警的动静……注意安全」。

这暴露了端到端链路的一个结构性风险：提示词第 1 条"只依据 events 陈述、不推测"，
在保护用户免受模型幻觉误导的同时，也**剥夺了大模型质疑上游检测结果的权限**。
检测层一旦出错，提示层会以可信的语气把错误传达给用户，而用户无从分辨。

结论：**大模型提示层不能作为精度兜底**。误报抑制必须在检测层通过阈值与去抖参数
解决；提示层能做的是措辞弱化，不能纠正错误事件本身。
